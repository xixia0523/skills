# 多 Agent 编排与源码复核

每次显式调用本 Skill 开展请求与返回/回调分析时，由主 Agent 负责需求澄清与编排，至少安排两个研究子 Agent 并发取证，并另设独立 Review Agent。本文规定协作方式；源码选择、证据等级和报告导读分别遵循 [source-routing.md](source-routing.md)、[evidence-policy.md](evidence-policy.md) 和 [source-walkthrough.md](source-walkthrough.md)。

## 1. 主 Agent 理解与澄清需求

主 Agent 先理解用户要研究的调用和问题，通过多轮对话逐步明确意图，直到以下信息足以决定分析范围：

- 准确 API、重载或调用代码，以及 Android 版本；
- 影响实际主链的产品、配置、权限、缓存或其他场景事实；
- 本次关心的是受理/投递、同步结果、业务完成还是回调/状态事件，以及应追踪到哪个可观察位置；
- 用户对输出的额外要求；未指定时沿用 Skill 的中文报告、源码讲解及父子步骤组织规则。

复用用户已提供的信息和项目默认值；只补问会改变选路、范围或结论的缺失项，不以固定对话轮数或重复确认作为开工条件。澄清期间可做必要的只读检查，但依赖未明确场景的调用链不能先按猜测定稿。子 Agent 的疑问由主 Agent 汇总后与用户沟通。

分派调用链研究前，主 Agent 整理共同研究约定：准确签名、场景与观察目标、已涉及仓库的固定 commit、源码位置、已证实的配置事实，以及待核实事项。新发现的仓库、基线差异或选路事实先回报主 Agent，再统一通知相关 Agent。

## 2. 拆分、编排与并发分派

按调用边界和依赖拆分任务，明确每项任务的输入、出口、交付物及上游依赖。典型分工如下，实际范围可按链路调整：

| 角色 | 主要职责 | 依赖与交付 |
|---|---|---|
| 主 Agent | 澄清需求、维护共同基线、编排任务、裁决冲突、整合最终报告 | 汇总各段证据，统一 R/S 编号、图、讲解和闭环结论 |
| 请求研究 Agent | 从选定 API 追到本次语义责任终点 | 提供实际调用、参数转换、执行上下文及返回/通知衔接点 |
| 响应/回调研究 Agent | 查找结果产生、返回恢复或回调注册与消费路径 | 提供结果到调用方可观察点的证据，并核对与请求的关联 |
| 独立 Review Agent | 直接读取固定版本源码核验研究产物及整合稿 | 不兼任被审内容的研究作者；输出可定位的问题与复核记录 |

至少两个独立研究任务并发执行；按宿主并发限制分批调度。存在前置依赖的部分等待上游证据就绪，其余取证可先进行。例如，响应 Agent 可先定位回调注册与接收入口，但责任终点及完成语义未确定前，只能提交候选证据与待确认关系。无回调的 API 按实际返回形式拆分，不添加虚构的回调任务。

分派消息至少包括：

```text
任务 ID 与负责范围：入口、出口、研究问题及不在范围内的内容
共同研究约定：API/场景/观察目标、仓库 commit、源码位置与已知配置
依赖与交接：需要等待什么，向谁提供哪些符号、数据和上下文
取证要求：固定源码、原始行号、调用片段及讲解；无法证实处明确标注
交付位置：指定的独立片段文件或结构化回复，避免同时改写最终报告
```

各研究 Agent 交付范围与基线、局部调用链、源码摘录及讲解、执行上下文和数据变化、请求/响应续接位置、已证实结论与缺口。引用须包括仓库、commit、文件、符号和原始行段；不能只交函数名列表或结论摘要。局部步骤可用临时 ID，最终映射由主 Agent 统一。

若宿主没有子 Agent 能力或无法满足并发要求，主 Agent 明确说明实际限制。可继续完成可用的静态取证，但须记录未执行的协作与复核环节，不得将单 Agent 工作描述为多 Agent 研究或已完成独立复核。

## 3. 主 Agent 汇总与衔接

主 Agent 结合原始证据整理各段产物，而非直接拼接子 Agent 文本：

1. 核对签名、源码 commit、配置与观察目标一致；有冲突时回到源码及选路事实，不能按多数意见裁决。
2. 核对段落接缝：调用与接收、投递与消费、参数与结果、请求暂停与响应恢复，以及回调是否属于本次观察目标。两段各自成立不等于它们之间的连接已证明。
3. 去重并统一父步骤功能、内部调用链、子步骤编号与锚点、图中箭头及证据账本；补齐影响完成语义的失败与清理路径。
4. 整理无源码依据的技术断言，在原位置改为范围明确的缺口说明；不得把未经证实的文字或箭头润色成确定结论。

最终报告由主 Agent 统一写入；研究 Agent 使用各自指定的交付位置。整合过程产生的新推断同样需要证据和独立复核。

## 4. 独立 Review Agent 对照源码复核

Review Agent 可以在研究期间核验已提交片段，最终必须审查主 Agent 整合后的报告。输入包含共同研究约定、受审正文版本或快照标识、完整报告及原始源码位置；研究摘要只能辅助导航。

Review Agent 直接读取相同 commit 的生产源码或明确标注的正式契约，逐项核对：

- 每个 R/S 及子步骤的调用双方、实际选中分支、参数和数据变化；
- 摘录与原文、行号、commit 是否一致，省略是否改变语义；
- 父步骤功能、内部调用链、总图与局部图的每个事实和箭头；
- 源码讲解、进程线程、同步异步、等待唤醒、回调交接及清理时机；
- 请求与响应能否衔接到本次可观察结果，证据账本及闭环结论是否成立。

所有描述当前实现的事实都应回溯到源码；找不到时就近写明“未取得源码”“无法访问”“实现闭源”或“尚未证实”，解释受影响步骤及可确认范围。无法获取不等于源码不存在。正式契约只证明其版本及外部语义，须标为 `CONTRACT` 并说明实现不可见；反编译、运行旁证和教学示意按各自类型标明，不能充当生产源码。无完整源码或正式契约覆盖的关键关系保留 `OPEN-GAP`，不能靠多 Agent 一致意见提升证据等级。

复核交付记录受审正文版本、源码基线、实际覆盖范围，以及逐项结果：

| 范围 / 步骤 | 原结论或待核事实 | 固定源码 / 契约定位 | 核对结果 | 问题、修正要求与处理状态 |
|---|---|---|---|---|
| R/S、图或结论 | 需要验证的关系或语义 | 仓库、commit、文件、符号、行段 | 已核实（SOURCE/CONTRACT） / 发现错误 / 无法核实 | 已修正并复核，或转为明确缺口 |

## 5. 修订、复核与交付

主 Agent 按问题记录补证或修订，再交 Review Agent 核对变更及受影响的上下游。找不到依据的断言须删除或改为明确的缺口与限制；不能只保留确定表述，再在文末追加免责声明。事实、图、步骤映射或闭环结论改变后，旧稿的复核结果不能直接用于新稿。

报告记录任务分工、最终受审正文版本、Review Agent、复核范围、问题处理和剩余缺口。复核状态分为“已复核”“部分复核”“未复核”，与 `SOURCE-CLOSED`、`CONTRACT-CLOSED`、`OPEN-GAP` 分开：全部待审项已核对，错误已修正并复核，无法证实处已准确改为缺口，才可写“已复核”；只抽查或仍有未处置的待审项时写“部分复核”。公开保留缺口的报告可以完成复核，但其闭环等级仍按最弱关键证据判断。

交付前由主 Agent 确认最终稿与复核记录一致。对话中除主链摘要、闭环等级、关键 gap 和报告路径外，还说明独立复核状态及影响结论的未解决问题。
