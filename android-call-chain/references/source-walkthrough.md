# 请求与返回的逐步源码导读

请求链和响应链中实际展开的 R/S 步骤都应有一组对应的源码调用片段，使读者能够沿调用点进入实现，再找到返回后继续执行的位置。仅作总览的父步骤通过内部调用链导航到子步骤的源码与讲解。步骤数量与深度由实际链路决定。

## 每一步如何组织

按以下顺序组织正文；短步骤可合并文字，一个步骤也可包含多个有序源码片段：

1. **执行上下文**：当前进程、线程或可证明的上下文，调用是否同步，以及何处发生切换。
2. **本步作用与数据**：说明整体功能、输入输出、关键转换和本步推进的责任层。涉及多个函数调用时，先按“多调用步骤：先总览再分解”一节给出内部调用链及子步骤导航。
3. **图与源码调用**：涉及驱动或内核时，先展示“驱动与内核：先图后源码”一节规定的局部调用图与执行说明，再展示调用点及必要的被调用实现；按执行关系编号，并分别标明文件、符号、原始行段及固定 commit 链接。
4. **逐段源码讲解**：在每个片段后就近解释其作用，简单逻辑简述，复杂逻辑展开；把条件、字段或返回值与当前请求的具体参数和状态对应起来。紧密关联的片段可合并讲解，但须覆盖每段的作用。
5. **后续入口**：用步骤 ID 与锚点指出继续下潜、等待、返回恢复或最终可观察结果的位置。

源码块应呈现实际语句，函数名列表、调用栈示意和源码链接用于辅助导航。动态分派还需交代实际接收者的确定依据；跨边界片段需能对应边界两端。

## 源码讲解的详略

每段源码都要有对应讲解，详略由理解当前链路所需的信息决定：

- **简单逻辑**：直接转调、字段读取、简单赋值或明确的参数传递，用一两句话说明做了什么、数据交给谁、为何进入下一步即可。
- **复杂逻辑**：涉及关键分支、数据编码与转换、状态机、锁与等待、异步调度、跨边界交接或影响返回时机的资源清理时，结合当前参数说明实际选中的路径、关键语句如何改变数据或状态、由谁继续执行，以及怎样到达后续步骤或恢复点。按有意义的代码段讲清机制，无须逐行翻译语法。

同样要求适用于请求和响应的全部子步骤。源码不可见时，讲清已有调用点与契约能证明什么、缺少什么；复用已有实现时，解释本次参数和上下文差异，并链接到原讲解。

## 多调用步骤：先总览再分解

一个 R/S 步骤涉及多个函数调用时，在该步骤开头、子步骤及源码之前给出：

1. **整体功能**：说明这一组调用共同完成什么，入口、关键输入和出口或结果是什么，以及它在上层主链中的作用。
2. **内部调用链**：用简短调用树、箭头链或 Mermaid 图列出本次路径的实际函数符号，标明调用层级、顺序及对应子步骤 ID，并链接到各子步骤。同步嵌套可画成调用栈；跨线程、跨进程时标明投递、IPC、消费或通知边界。
3. **子步骤源码导读**：需要分解讲解时，按 `R8.1`、`R8.2`、`R8.3` 或 `S8.1`、`S8.2`、`S8.3` 编号；各子步骤沿用执行上下文、源码与出处、逐段讲解、后续入口的结构。父步骤负责总览，源码在所属子步骤展示。

下面仅演示父步骤的组织方式，函数与职责均为教学占位，实际报告须按目标版本替换并添加子步骤链接：

```text
R8：准备请求并提交给传输层
Entry.submit()
├─ R8.1 Request.prepare()       准备本次请求数据
└─ R8.2 Transport.send()        将请求交给驱动入口
   └─ R8.3 Driver.writeRequest() 执行实际写入
```

子步骤编号表示父步骤内的阅读顺序，调用嵌套由图或缩进表达。短小的多调用步骤可只给简短调用链并合并讲解，无须为每个简单辅助函数另建标题。若底层局部图已完整表达内部调用及子步骤映射，可兼作父步骤总览。

S 步骤同样先说明整体功能，再梳理实际的结果产生、返回恢复或通知消费链，并关联对应 R 步骤的暂停位置。按源码区分原调用栈逐层返回和新的回调入口；响应链的函数与顺序须独立核实。

## 驱动与内核：先图后源码

第三章请求链、第四章响应链只要涉及驱动或内核实现，就在各章对应的连续底层子链开始处，加入 Mermaid 局部调用图。图放在该段第一步的源码之前；同章有不连续的底层子链时分别画图，连续步骤可共用一图并标明覆盖的 R/S 编号。第二章总时序图用于全链导航，不能代替这两章的局部图。没有进入底层的章节无需凑图，也不因此扩大责任终点。

图的目标是让暂时读不懂底层代码的读者，先看懂“谁在执行、工作交给谁、谁等什么、谁使等待结束、恢复后从哪里继续”，再把节点与源码语句对应起来。

### 图中如何表达执行关系

- 默认使用 `flowchart`，以进程和线程/执行上下文分组，节点写实际函数或关键操作，并注明用户态/内核态。`ioctl`、`read` 等系统调用进入内核时，通常仍是原调用线程；不要将“内核”画成独立服务进程，也不要把内核态等同于内核线程。实际使用 kworker、内核线程、硬中断或软中断时，单独标明有证据的上下文；中断上下文不能标为可睡眠的普通线程。
- 图例在图旁说明：实线 `-->` 表示同一执行上下文内的调用、状态检查或恢复顺序，虚线 `-.->` 表示排队、跨上下文交接或通知/唤醒；每条边用文字写明具体机制。虚线不能代替实际的队列、消费者或调度证据，也不表示目标立即执行。
- 跨线程/跨进程交接同时画出投递点、队列或共享状态和消费入口。标出任务由谁消费；队列、等待队列和 completion 是数据结构，不是执行线程。返回箭头需区分原调用栈恢复、IPC reply 和 callback 入口；回调是否运行于原线程，以源码为准。同步 Binder 嵌套事务可能复用原调用线程，图中应标为同线程重入，不能误画成外层调用已经返回，也不能强制分配新线程。
- 图中实际调用节点、条件和交接边标注对应 R/S 步骤 ID，并在图下链接到相关步骤及其固定版本源码。步骤跨章时，第三章的等待节点注明第四章恢复步骤，第四章的恢复节点注明第三章暂停步骤。图里的条件和唤醒关系与源码使用同一粒度，不能用熟悉的 Binder 或驱动模式补齐未知实现。

### 等待必须画出什么

有阻塞时，图中明确画出等待位置、等待条件、条件不满足时的去向、使条件成立的生产者/事件，以及条件成立后的消费与恢复。若源码允许已有数据、条件已满足而直接继续，应保留该路径，不画成每次必然睡眠。存在循环检查时也要画出回到条件检查的边。

等待期间说明当前线程是阻塞/睡眠、忙轮询，还是继续执行其他工作；按实际代码描述，不一概写成“等待”。同步 Binder 等待回复期间若处理嵌套事务，应展示重入入口及其返回后继续等待的关系。唤醒只使任务具备被调度的条件，不能画成“唤醒即返回”；阻塞路径应区分被唤醒、获得调度、按源码重新检查条件和继续执行。若存在超时、信号中断或取消，引用第五章对应路径，不混成正常业务完成。

图后用简短文字或下表回答执行与等待问题；没有等待时直接说明原因，不保留空表：

| 执行者（进程 / 线程 / 模式） | 本段动作与交接对象 | 等待点、条件及机制 | 使条件成立并通知的一方 | 恢复入口与完成含义 |
|---|---|---|---|---|
| `<可证明的上下文>` | `<同步调用或异步投递；数据去向>` | `<实际符号、条件、队列/completion/...；或不等待>` | `<生产者、状态写入及通知机制；或不适用>` | `<关联 R/S 步骤；受理/传输/业务结果>` |

### 请求图与响应图分别讲什么

- **第三章请求图**：从用户态发起点进入内核/驱动，展示关键函数、数据排队或交接及执行者。同步接口注明原调用尚未返回，在哪里等待、等待哪类事件；异步接口注明返回的是受理还是业务完成，按本次范围展示后续消费；接口提供完成通知时，再说明通知由谁承担。一个同步 API 内部也可能包含异步排队，不能用一个“同步”标签覆盖整段流程。
- **第四章响应图**：根据本次观察目标，从受理状态、业务结果或状态事件的产生处展开，展示实际返回、通知或等待恢复过程，追到调用方可观察的位置。只承诺投递的接口展示受理返回或提交确认；契约不提供业务完成通知时明确写出，不添加虚构的反向业务箭头。存在等待时再画条件、唤醒及恢复。图与第三章使用一致的进程、线程和等待对象名称；回调链按实际消费上下文画，同线程重入与原调用栈恢复分别标明。
- **语义区分**：函数返回、入队成功、传输完成、线程唤醒、业务完成、调用方观察到结果是不同事件。以同步 Binder 为例，不能把 `BR_TRANSACTION_COMPLETE` 当成业务 reply；是否等待 `BR_REPLY` 以及如何继续，应由目标版本实现证明。异步/oneway 也不意味着提交过程绝不会因资源或锁而短暂阻塞。

[报告模板](../assets/call-chain-report-template.md) 中的两张局部图是结构骨架，不是任何版本驱动的实际调用链。生成报告时按源码替换符号与条件，删除不适用节点，补全真实的队列、消费入口和中间步骤。每张图后用几句白话说明阅读顺序和关键术语，并指向本段源码；图片或示意本身不提升证据等级。实现不可见时在边界处标注 `CONTRACT` 或 `OPEN-GAP`，不要虚构内部线程、等待队列或唤醒动作。

## 按执行阶段展开

- **调用与恢复分开**：请求章节展示准备、下潜和等待；响应章节从结果产生处展开，回到原调用点之后的续接位置。同一函数可拆成多个阶段，标明它们属于同一次调用。
- **保留必要上下文**：被调用者内部发生的重要解码、路由、排队或状态转换继续展开。直接调用和 JNI 本身不意味着切换线程。
- **区分绑定与执行**：JNI 注册表、虚函数接收者来源、syscall 宏、函数指针绑定和线程池启动，标注为既有状态或编译时连接证据；实际调用发生处引用这些证据。
- **排队是因果连接**：同时定位投递与消费入口，说明消费线程从哪里继续。跨线程步骤编号表示依赖关系；并行、竞态和调度不确定性应在相应位置说明。
- **核对完成语义**：先按 API 契约及用户范围确定观察目标，再区分接口受理、入队成功、驱动确认、业务完成和调用方观察结果。仅承诺投递的接口可闭环到受理结果，不要求不存在的业务完成通知；若契约承诺或用户明确要求业务完成，再追踪 callback、Future 或状态事件。用户要求的目标无法证明时保留限制或 gap，不能缩小到受理成功后宣称业务闭环。
- **返回包含必要清理**：解释 `finally`、析构和资源所有权对返回时机的影响。返回表达式已经求值，不等于调用方已完成赋值；回收包装对象也不必然释放底层数据。

下面以同步 Binder 的几个位置说明如何拆分阶段，编号应随实际报告分配：

| 位置 | 本阶段展示的语句或行为 | 续接说明 |
|---|---|---|
| 请求：Proxy 调用 | `mRemote.transact(...)` 及其下潜实现 | 此调用尚未返回；解码 reply 留在响应步骤 |
| 请求：等待函数 | `talkWithDriver()` 发出命令并等待 | 暂停在调用处，标明收到响应后的恢复步骤 |
| 响应：等待函数恢复 | 处理 `BR_REPLY`，挂接接收数据 | 沿原调用栈返回 Proxy |
| 响应：Proxy 恢复 | `readException()`、读取业务结果、`finally` | 清理完成后返回，调用方才观察到业务结果 |

表中符号只用于说明阶段划分；实际报告仍须取得目标版本的对应源码。Handler、Executor 等异步链按本次观察目标选择展开投递、消费、业务完成及结果观察阶段，不强制每个接口都具有这些阶段。

## 源码选取与截取

- 选取足以解释本步的最小连续行段，保留函数签名或明确所属符号、关键条件、参数与数据操作。一个步骤需要多段时，按调用关系排列；原文件行号不必递增。
- 每段在代码块外标明仓库、文件、符号、行段和 commit 出处；仓库及 commit 可通过基线代号和固定链接关联。多段来自不同文件时分别标注，不能共用一个模糊出处。
- 摘录保持原语句、标识符和关键条件，允许统一缩进。省略位置用清晰的注释标出；跳到同文件另一函数时说明位置变化，导读注释标为补充说明。
- 同步保留与判断相关的分支边界，或将条件与完整选中分支拆成单独片段并解释。避免保留未选分支的半截 `if/else`、错误日志或 `goto`，使正常路径看起来进入异常处理。
- 明确代码块是局部摘录，是否可独立编译由内容决定。条件分支或调用语句的省略不能改变读者对当前路径的判断。
- 类型、绑定、构建条件和错误处理仅展开理解当前主链所需的部分。深度由 API 责任终点和用户范围决定；内核、驱动与完整初始化链按其相关性展开。

## 区分片段来源

| 来源 | 报告中如何标识 |
|---|---|
| 固定版本生产源码 | 标明原文件、行段与 commit，按原始语句摘录 |
| 构建产出的生成代码 | 记录生成物来源、接口输入及可确认的版本或构建信息 |
| 根据接口和生成器推导的代码 | 明确标为“生成规则推导片段”，引用接口、固定版本生成器和决定语句的构建条件；未知条件不得写成已验证生成物 |
| 解释性示意或伪代码 | 明确标为教学示意，与生产摘录分开，不能承担调用箭头的证据 |
| 契约或反编译结果 | 分别标为 `CONTRACT` 或 `BINARY`，说明可确认范围；缺少实现时保留相应限制或 gap |

片段的展示形式不改变证据等级，闭环仍按 [evidence-policy.md](evidence-policy.md) 审计。源码不可见时，在该步骤展示已有调用点、可用契约及缺失部分，不能用推测代码填满源码块。

## 阅读导航与复用

- R/S 步骤 ID 与时序图、证据账本一致，子步骤保留完整编号（如 `R8.2`）和独立锚点（如 `r8-2`）。每条实际调用箭头对应到具体步骤的证据；仅作总览的父步骤链接到子步骤，避免重复记账。较长链路在请求章节前增加阶段导航，并明确响应章节从哪个责任终点继续。
- 同一机制复用时，当前步骤保留本次实际调用点、参数差异及执行上下文，再链接到已展示的共用实现。避免只写“同上”或重复整段底层实现。
- 实际展开的步骤默认在报告内展示源码组，便于连续阅读。片段长度按语义需要调整；辅助完整源码或较大摘录可另存并链接。
- 对片段多的报告，可保存源码索引、行段与内容摘要辅助复核。输出位置随当前任务确定，skill 不依赖某次分析的临时文件或特定报告。
