# Android 全链路源码闭环分析

以 Demo 中的真实调用为起点，形成可逐跳核验的用户态源码链路，并解释内核/驱动的概念边界。按实际实现追踪；不强行套用所有层级，不用架构常识填补源码缺口。默认用中文输出，保留源码标识符原文。

## 1. 前置校验

本节仅在执行调用链分析时生效；创建、编辑或评审本 Skill 不要求提供 Demo。

分析前必须已提供以下两项。任一缺失时，不读取项目、不检索源码、不调度分析任务、不创建分析文档；只索取缺失项并等待：

| 必填输入 | 要求 |
| --- | --- |
| `DEMO_SOURCE` | Demo 代码的本地路径、仓库地址或可访问的代码内容。 |
| `TARGET_CALL` | Demo 中明确指定的 API 调用点，或第三方框架回调的生命周期实现。 |

输入齐全后，确认 Demo 可读取且入口可唯一定位。路径不可达、仓库不可访问，或有多个无法区分的调用点时，说明问题，索取必要信息并等待，不擅自替换入口。

再读取可选参数：

| 参数 | 默认值 | 处理方式 |
| --- | --- | --- |
| `AOSP_VERSION` | 执行时核实的 Android 13 `android-13.0.0_rN` 系列最新稳定发布 tag | 用户指定则覆盖；主 Agent 必须解析、验证并锁定唯一完整 tag。 |
| `FRAMEWORK_IMPL_BASIS` | 无 | 从 Demo 的 Gradle 依赖、import、注释及说明文件提取；用户提供的信息也须与 Demo 核对。 |

### 第三方框架源码可达性：硬性门槛

仅检查目标链路实际涉及的第三方框架。若 Demo 直接调用 Android API 且链路不涉及第三方框架，记录“不适用”并继续。

1. 从 Gradle 声明、版本目录、锁定文件或依赖解析结果确定实际依赖坐标及版本；结合 import、注释、README 等确认框架身份。声明版本与解析版本不同时，以有证据的实际解析版本为准。
2. 根据上述依据定位官方开源仓库，实际打开源码，验证可公开访问。通过发布元数据、官方 tag、commit 或同版本 sources 包，证明源码与 Demo 依赖版本对应；import 本身不能证明版本。
3. 出现下列任一情形，终止整个分析任务，不创建分析文档：实现依据缺失而无法定位来源；仅有 aar/jar 二进制且无公开源码；源码版本与实际依赖版本无法对应。不得用反编译结果或“相近版本”绕过门槛。
4. 终止回复列出：缺失项或失败原因、已尝试的定位路径、用户需补充的信息。网络或权限问题导致无法验证时，也说明验证受阻并停止，不将其断言为源码未公开。

### 锁定版本与来源

- 未指定版本时，从 [AOSP 发布版本说明](https://source.android.com/docs/setup/reference/build-numbers) 与 [官方 manifest tags](https://android.googlesource.com/platform/manifest/+refs) 核实 Android 13 发布 tag，按数字比较 `rN`；排除预览、测试及其他版本系列。无法验证时停止并说明需要的版本信息，不凭记忆填写“最新”。
- 在分工前，将唯一 tag、核实来源及日期传给所有 Agent。AOSP 源码统一引用该 tag 下的文件，例如 `https://android.googlesource.com/platform/<repo>/+/refs/tags/<tag>/<path>#<line>`；实际访问并核对，不仅拼接 URL。
- Demo 记录 commit 或本地文件及行号；第三方框架单独锁定对应版本和 commit。AOSP 同一 tag 下的多仓库构成平台基线，不把第三方版本写成 AOSP tag。
- 明确这是指定 AOSP 基线的实现分析；未提供设备构建证据时，不声称它就是设备上的厂商实现。入口在基线中不存在或不兼容时，说明版本冲突并停止受影响分支，不静默换版本。

## 2. 执行编排

### 主 Agent：规划、编排、汇总、质检

1. 完成输入、第三方框架门槛和版本锁定，明确目标场景及所需的回调/返回路径。
2. 调度 A、B、C。A 先给出已验证的 Framework 入口，再让 B 从此入口向下追踪；C 可并行收集相关概念资料，但最终交叉校验必须等待 A、B 产出。若运行环境没有子 Agent 能力，按 A→B→C 的职责顺序执行，并披露未进行独立 Agent 复核。
3. 给每个任务相同的版本声明和目标边界，要求返回逐跳证据表、交界记录、缺口清单。交界记录至少含：调用者与被调用者完整签名、两端源码位置、进程/线程、传递机制及同步异步语义。
4. 汇总后消解交界不一致，按 §5 逐项验收。能通过补查源码修复的项退回对应 Agent；源码确实无法取得的项保留为缺口，终止该分支，禁止编造或无限重试。
5. 只有证据链闭合时才声明“闭环”。正式追踪中遇到缺口，可输出已证实部分并标记“部分闭环（存在缺口）”；这与前置硬性门槛失败时“不产出文档”不同。

### A：App + 第三方框架源码追踪

- 从 `TARGET_CALL` 向上定位 Demo 中触发它的业务逻辑、触发条件及调用上下文，向下追到 Framework API 的 Java/Kotlin 边界。
- 若目标是框架回调，先追踪其注册、保存、触发、分发到用户回调的真实实现，再继续跟踪相关 Framework 调用；不能只列用户 override 方法。
- 每跳记录类名、完整方法签名、源码链接、所在进程、线程及同步/异步语义。以明确的 Framework 入口交接 B，不凭 API 名称猜下层链路。

### B：Framework + Native/HAL 源码追踪

- 从 A 交接的入口沿实际路径追到内核/驱动的用户态边界。System Service、JNI、Native Library、HAL 是可能经过的层，不是固定顺序；不经过的层标记“未经过/不适用”并给依据。
- 分别标注 App 进程、`system_server`、独立 native 服务或 HAL 服务的实际进程名；禁止用“Framework 进程”笼统代替。Framework 类也可能在 App 进程内执行。
- 线程标明调用者线程、Binder 线程池或有名的内部工作线程，并给出入口/切换依据；不能根据进程名猜测线程。Handler、Executor、Looper、消息队列等切换需列出投递和执行两端。
- Binder 跨进程调用标注接口、方法、是否 `oneway` 及 `binder` / `hwbinder` / `vndbinder` 通道的证据。HAL 标明 Legacy HAL / HIDL / AIDL HAL 及具体接口版本；采用 passthrough 或进程内调用时按实际标注，不虚构 IPC。
- JNI 需核对 Java native 声明与注册映射；生成的 AIDL/HIDL 胶水可引用同 tag 的接口定义及生成依据，明确是生成代码，不能伪造不存在的生成文件链接。
- 说明同步调用返回的含义。同步 Binder 返回只证明该次事务完成；业务工作可能随后由工作线程处理，并通过回调完成。回调按实际语义标注，不能一律视为异步。
- 遇到闭源厂商实现、条件分支无法确定，或进程/线程/下一跳缺乏证据时，将相关结论记为缺口并停止该分支。不要拿另一设备或另一版本的实现补齐。

### C：内核/驱动概念讲解 + 交叉校验

- 只做概念与过程讲解，不追踪、摘录或编写内核/驱动源码及伪代码。解释已确认的子系统角色、用户态入口机制（如 ioctl、sysfs、字符设备、系统调用）、控制流和数据流的基本路径。
- 从 B 已确认的用户态边界开始说明，引用实际访问过的 [Linux 内核文档](https://docs.kernel.org/)、[LWN](https://lwn.net/) 或 [AOSP 官方文档](https://source.android.com/docs)。区分通用机制与有证据的设备实现，不猜测厂商驱动名称或内部细节。
- 交叉校验 A→B→C 交界的完整方法签名、源码位置、进程、线程、同步/异步及传递机制；检查回调和返回路径是否与正向调用一致，输出缺口清单。
- 内核层按约定只讲概念，本身不算源码缺口；无法确认用户态如何到达内核边界才是缺口。若调用只在用户态完成，明确说明内核/驱动分析不适用，不补造硬件路径。

## 3. 逐跳证据规则

- 调用链必须能从调用者定位被调用者：在源码链接旁写出文件路径和完整签名；链接尽量定位到行。说明关键参数、回调对象或接口实例如何传到下一跳，避免仅罗列同名方法。
- 本地 Demo 或用户直接粘贴的代码可用可访问的本地文件链接及行号；粘贴代码保留文件标识和编号片段。公开仓库使用固定 tag/commit 链接，不强求用户把 Demo 公开。
- 证据需覆盖方法体中的实际调用、接口派发/注册和线程切换；API 文档、搜索摘要和方法名相似不能代替实现证据。无法取得的源码链接或无法核实的语义进入缺口清单。
- 给已证实事实、概念性解释和仍待核实的结论明确边界。每项缺口记录最后已验证节点、缺失的下一跳或属性、已查路径、影响范围及补齐所需信息；图中止于该节点。

## 4. 输出文档

读取 [references/report-template.md](references/report-template.md)，严格按其中的 §0–§6 输出单一 Markdown 分析文档。模板用于结构，不是事实来源；替换全部填写项，不额外生成分层报告或图文件。

全文仅包含一张 Mermaid `sequenceDiagram` 总览图：

- 用 `box` 按进程分组；每个 `participant` 对应明确的“进程 / 线程 / 组件”。同一进程的不同线程分别列泳道，IPC 和进程内调度均应可辨认。
- 遵循用户约定：同步调用和同步返回均用实线 `->>` 并显式标注“同步调用”或“同步返回”；异步投递、异步回调及 `oneway` 用虚线 `-->>` 并标明具体语义。同步回调仍用实线，不套用通常的虚线返回画法。
- 每条消息关联正文的逐跳编号；投递与实际执行分别展示。只画已证实的路径，缺口用 Note 标明并终止；内核最多表示概念边界，不展示内部源码步骤。
- 若实际路径只有用户态或不经过 HAL，图和正文均保持这一事实，不为满足标题补充虚构参与者。发现缺口后也保留唯一总图，清楚显示闭环止点。

## 5. 验收清单

| 检查项 | 通过条件 |
| --- | --- |
| 输入完整 | `DEMO_SOURCE` 与 `TARGET_CALL` 均存在且可定位；否则未启动分析。 |
| 框架可达 | 目标涉及的第三方框架源码可公开访问且版本可对应；否则已终止且无分析文档；无第三方框架时标记不适用。 |
| 版本一致 | §0 声明唯一具体 AOSP tag，所有 AOSP 实现引用均使用它；Demo、第三方版本另行记录。 |
| 源码闭环 | App/Framework/Native/HAL 的实际每跳有可访问证据；未经过的层有依据，缺口已声明且终止该分支，未冒称完整闭环。 |
| 时序图 | 仅一张 Mermaid 总图，按进程/线程分泳道，实线同步、虚线异步/oneway；返回与回调语义无歧义。 |
| 进程标注 | 每跳明确实际进程，无“Framework 进程”等笼统结论；未知归属已记缺口。 |
| 线程标注 | 每跳明确线程或有证据的线程角色，切换有实现依据；未知归属已记缺口。 |
| IPC / HAL | 已确认 Binder 通道、oneway 及 HAL 类型/版本；无相关边界时说明不适用。 |
| 驱动层 | 仅概念与过程讲解，有可靠来源，无内核源码、伪代码或厂商实现猜测。 |
| 衔接一致 | A→B→C 签名、版本、进程、线程、同步/异步及回调/返回路径一致，缺口清单完整。 |
| 可学习性 | 初学者可按图中编号找到正文、入口文件与下一跳，而非只看到抽象层名。 |

在文档 §6 逐项给出“通过 / 不适用 / 未通过（缺口）”及依据。未通过项必须处理或明确披露后再交付。
